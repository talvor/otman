How should otman rewrite frontmatter?

The same hand-written note is shown with each option, after otman edit OTM-4 --add-label needs-info. The decision comes down to one thing: does byte-identical frontmatter matter, or is “stable after the first write” enough?

The note before the edit

A

Splice

recommended

Parse with go.yaml.in/yaml/v3 Nodes only to read values and locate keys. On write, re-serialise just the changed key and splice it into the original bytes. Frontmatter is flat, so a key's span runs from its line to the line before the next key, with trailing blank and comment lines trimmed off. New keys go just before the closing ---; a removed key's span is deleted.

Pros

  • Every unintended byte is untouched: blank lines, comments, quoting, indentation, user keys. This is exactly ADR 0005's promise.
  • Git diffs and sync conflicts touch only the changed key.
  • G7's round-trip test can require byte-identical output.

Cons

  • otman owns about 200–300 lines of span code, plus a fuzz test.
  • A rewritten key loses its own trailing comment (# triage queue above). Nothing else does.
  • Flow-style frontmatter ({id: OTM-4, …} on one line) can't be spliced.
Safeguards: after splicing, re-parse and check that every other key is semantically unchanged, otherwise refuse with unsafe_write. Flow-style frontmatter also gets unsafe_write and is reported by doctor.
B

Round-trip through yaml.v3 Nodes

Parse the whole block into a Node tree, change the labels node, and re-encode the whole block.

Pros

  • Simplest: one well-known library, no byte-position code.
  • Always valid YAML, and flow style works.
  • Comments, key order and node style (quoting, flow vs block) are kept by the parser.

Cons

  • Normalises the whole block: blank lines between keys disappear, the encoder sets indentation, and comments can drift (yaml.v3 is known to move foot comments).
  • The first write to a hand-edited file gives a noisy diff. It's stable afterwards, so the noise happens once per file.
  • ADR 0005's wording needs softening, and G7 becomes “stable after first write”, not “byte-identical”.
C

goccy/go-yaml AST

unverified

goccy keeps a token-level AST that remembers the original formatting. Edit the AST and print it back from its tokens.

Pros

  • Closer to byte-preserving than B, with no splicing code of our own.

Cons

  • Fidelity depends on how goccy prints its tokens, which is less proven in edge cases than yaml.v3, and its bugs become otman's.
  • More complex API for attaching comments.
  • I haven't verified its byte fidelity; a quick prototype would settle that.
