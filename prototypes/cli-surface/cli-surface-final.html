Complete command index

Prefix every command with otman. Global flags: --vault PATH --project KEY --actor NAME --format human|axi|json, plus --json. REF accepts a qualified ID, a number within a Project, a unique full filename, or an exact Vault-relative path.

Query filters: --state open|closed|all; --kind KIND; repeatable --label LABEL (AND); --assignee NAME|@me or --unassigned; --parent REF; --blocked-by REF; --search TEXT (case-insensitive title/body substring).

Scope: --project KEY or --all-projects. Paging: --limit N / --offset N or --all. Stable order is Project key, then number ascending. Paging reads live data, not a snapshot.

Exit codes: 0 success, no-op or empty result; 2 invalid arguments/config/input; 3 not found; 4 conflict/ambiguity/invalid relevant graph; 1 I/O or unexpected failure. Error details go to stderr; stdout is empty on failure.

Accepted contract from rounds 1 and 2

Expand a section to check the full decisions. The completions above clarify these where noted.

Q1 · Command grammar

Flat verbs (recommended): otman create / view / list / edit / comment / close / reopen / claim / release / frontier. Project and config commands get their own groups.

Flat verbs keep frequent commands short. Use --kind issue|prd|spec, defaulting creation to issue. Relations use parent set/clear and block/unblock; labels and assignment use edit flags.

Q2 · Find the Vault and Project

Repo pointer + machine config (recommended): .otman.toml in the code repo stores project = "OTM"; user config stores the absolute Vault path. Flags override env vars, which override the pointer/default config.

Keep machine paths out of git. Find the nearest .otman.toml up to the repo root; an unknown Project is an error. Explicit Item IDs can identify their Project. No silent choice of the first Project.

Q3 · Who is @me?

Configured identity (recommended): --actor > OTM_ACTOR > user config actor. @me resolves to that value. Missing identity fails commands needing an author or claimant.

Configured identity is predictable across repos and devices. Assignee and comment author remain plain strings, without authentication or a user directory. Agents can act as talvor or use an explicit agent identity.

Q4 · Default output

Auto (recommended): readable human output on a TTY, compact AXI-style output when piped; --format human|axi|json always overrides.

The prototype below switches all three renderings of the same result. JSON is the stable scripting contract; compact output uses named fields. Later rounds will pin down truncation, errors and exit codes.

Q5 · Claim conflicts

Guarded claim (recommended): claim succeeds only when unassigned; claiming again as the same actor is a no-op; another assignee causes a conflict. Explicit reassignment uses edit --assignee.

This is the command contract. Cross-device guarantees depend on the number-safety work and must not be implied by this in-memory demo. Release requires the current actor; explicit edit can clear or change another assignment.

Q6 · What belongs on the frontier?

Open, unclaimed, with no open blockers (recommended). --parent OTM-1 limits to direct children. Missing blocker targets cause a diagnostic, never silently count as closed.

Use list for general filtering. Frontier should match the takeable-work definition the wayfinder skill already uses. Transitive descendants can be a separately explicit option if needed.

Q7 · Setup and discovery

Explicit setup (recommended): config set vault <absolute-path>; config set actor <name>; project create <KEY> --name <name>; project link <KEY> writes .otman.toml in the current repo root. No prompts or implicit Project creation.

User config: $XDG_CONFIG_HOME/otman/config.toml, falling back to ~/.config/otman/config.toml. Vault: --vault > OTM_VAULT > config. Project default: --project > OTM_PROJECT > nearest repo pointer > config project. Outside a git repo, search for a pointer up to the filesystem root. Config show reports effective values and their sources. project link refuses to replace a different pointer unless --force is explicit. project list/view expose existing Projects.

Q8 · Item references and Project mismatches

Qualified ID wins over defaults (recommended); an explicit conflicting --project is an error. Bare 3 requires a selected Project. Also accept the exact Vault-relative Item path to disambiguate collisions.

No title search or fuzzy matching when selecting a mutation target. Duplicate IDs fail and list candidate paths, as settled in number safety. Full filenames also resolve when unique; paths remove any remaining ambiguity. Cross-Project relation references follow the separate relation policy below.

Q9 · Bodies and comments

--body <text> or --body-file <path>, with --body-file - reading stdin (recommended). Reject both together. create requires --title; omitted body is empty. comment requires non-empty text. edit body replaces only the main body, preserving stored comments.

No automatic editor in the recommendation. --clear-body explicitly empties the main body. A body/comment file is UTF-8 Markdown. Kind-specific templates remain a separate map decision. Appending a comment is intentionally not retry-idempotent; comment updates/deletion are outside this proposed v1 surface.

Q10 · Editing and state changes

Explicit delta flags (recommended): edit --title/--kind/--assignee; --clear-assignee; repeatable --add-label/--remove-label. close and reopen are separate commands. Reject contradictory flags; validate the entire operation before changing the Item.

Repeated additions/removals and close/reopen of an already matching state succeed with changed=false. Empty edit is an error. Retitling rewrites links; changing Kind moves the file. No implicit child cascade on close. Project moves and label vocabulary remain separate map decisions; this round does not settle them.

Q11 · Lists and frontier queries

Bounded queries (recommended): list defaults to open Items in the selected Project; --all-projects explicitly spans the Vault. Default limit 50, --limit/--offset and --all. Sort by Project key then number ascending; frontier uses the same order and paging.

Filters: --state open|closed|all, --kind, repeatable --label (AND), --assignee <name|@me>, --unassigned, --parent <ref>, --search <text> (case-insensitive title/body substring). frontier accepts the applicable filters but fixes open/unassigned/unblocked. --parent is direct children; list --blocked-by <ref> finds dependents, view includes children and relations. Include total, returned count and has_more; no matches is success. No recursive descendants flag in v1. Pagination is over live data, not a snapshot.

Q12 · Parent and blocker rules

Same Project only (recommended): one parent per Item; any number of blockers; forbid self-edges, missing targets and cycles within either graph. Parent and blocking graphs are independent.

Edges to closed Items are allowed; only open blockers exclude an Item from the frontier. Adding an existing edge or removing an absent edge is a successful no-op. Setting another parent explicitly replaces the old one. Closed parents may still have open children. No relation implies another relation. Malformed or ambiguous relevant links make the operation fail rather than return an unsafe partial frontier.

Q13 · Can blocked work be claimed?

Claim any open Item (recommended), including blocked work; reject closed Items. frontier is the ready-work picker, while claim is guarded assignment. Same actor on an open Item remains a no-op.

Explicit edit --assignee can assign any status. Release is permitted on either status, is a no-op when already unassigned, and conflicts if assigned to someone else. Same-device locking covers the check and write. Two agents configured as the same actor share a claim identity; this does not provide session-exclusive ownership.

Q14 · Output size and success records

Compact human/AXI view (recommended): body preview up to 2,000 characters, comments only with --comments; --full removes text limits. JSON view is complete and includes comments. Lists contain summaries; mutations return Item summary plus changed.

Always mark truncation and show the retrieval command. --json is a convenience alias for --format json; conflicting format flags fail. JSON has schema_version:1, data and warnings; collections add total/count/has_more. Item summaries carry id, title, kind, status, labels, assignee, parent, blocked_by and path. create/comment are not inherently retry-idempotent. Full view adds body, comments and timestamps.

Q15 · Errors and automation

Structured failures (recommended): nonzero exit, empty stdout, diagnostic on stderr in the selected format. JSON stderr uses schema_version:1 and error {code,message,details,hint}. Success stdout contains only the result.

Proposed exits: 0 success/no-op/empty query; 2 invalid arguments, config or input; 3 not found; 4 conflict (claimed, ambiguous ID, invalid graph or inconsistent relevant data); 1 I/O or unexpected failure. Stable error codes distinguish cases. Duplicate-number warnings accompany otherwise valid results; exact-path operations remain available. JSON warnings stay in the success envelope; human/AXI warnings go to stderr. No progress chatter on stdout.
